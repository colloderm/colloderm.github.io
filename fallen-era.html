클래스 구조 Architecture

모든 건설물은 AFEBuildPiece 하나를 부모로 두고, 상호작용 · 피해 · 팀 판정을 인터페이스로 받습니다. 피스의 메시 · 비용 · 소켓 · 내구도는 코드가 아니라 UFEBuildPieceDefinition 데이터 에셋에 있어서, 새 피스는 대부분 에셋만 추가하면 됩니다.

UFEBuildingComponent

캐릭터에 붙는 건설 담당 컴포넌트입니다.

  • 빌드 모드 전환, 고스트 미리보기와 배치 검증
  • 배치 · 철거 · 망치 수리 · 업그레이드 서버 RPC
  • HUD를 직접 알지 않고 델리게이트로 상태 변경만 알림
UFEBuildHudComponent

건설 UI와 패널 RPC를 맡습니다. 리뷰 후 건설 컴포넌트에서 분리했습니다.

  • MVVM 뷰모델, 빌드 메뉴(건설 · 가구 · 방어 탭)
  • 재료 투입 · 보관함 · 화로 · 탄약 패널
  • 의존 방향은 HUD → 건설 한쪽뿐
UFEBuildingSubsystem

월드 단위로 모든 피스를 관리하는 서브시스템입니다.

  • 지지 거리 재계산과 붕괴 큐
  • 피스 레코드 저장 · 복원
  • 건설 에셋 미리 로드, 로컬 안내 문구
UFEBuildPieceDefinition

피스 하나를 정의하는 UPrimaryDataAsset입니다.

  • 메시 · 필요 재료 · 최대 체력 · 소켓 목록
  • 업그레이드 대상(나무 → 돌 → 철 사슬)
  • 에셋은 모두 소프트 참조 + Asset Manager 비동기 로드

소켓 스냅 & 배치 검증 Placement

  • 피스마다 데이터 에셋에 소켓(종류 태그 · 허용할 상대 종류 · 위치)을 둡니다. 커서가 소켓 반경 150cm 안에 들어오면 그 자리에 붙습니다.
  • 한 소켓에 붙는 방법이 여럿이면 Q/E로 후보를 고릅니다. 삼각 벽 좌우 반전, 계단 방향 선택이 이 방식입니다.
  • 고스트 검증은 움직일 때 최대 20Hz, 멈췄을 때 0.25초 주기로 돌리고, 클릭하는 순간 한 번 더 검증합니다.
  • 서버는 받은 위치 · 회전으로 처음부터 다시 검증합니다. 위치는 정수 cm, 회전은 uint8 단계로 보내 패킷을 줄였습니다.
  • 같은 자리 겹침, 공중 배치, 플레이어 · 적이 서 있는 자리, 토대 밖으로 뻗는 천장을 막습니다.

구조 안정성 & 연쇄 붕괴 Structural Support

땅에 닿은 피스(anchor)에서 멀어질수록 지지 거리가 커지고, 재질마다 정해진 한계를 넘으면 지을 수 없습니다. 받침이 부서지면 거리를 다시 계산해, 땅까지 이어지지 않는 피스를 순서대로 무너뜨립니다.

0토대땅에 닿음→ 1벽→ 2천장→ 32층 벽
×토대 파괴→ 255벽→ 255천장→ 2552층 벽 땅까지 이어지지 않음 → 붕괴 큐에 넣고 0.1초마다 하나씩 파괴 
// FEBuildingSubsystem.cpp — 지지 거리 재계산 (일부)
// 정수 비용 다익스트라. anchor(땅에 닿은 피스)가 출발점.
while (Frontier.Num() > 0)
{
    // 프론티어에서 거리가 가장 짧은 피스를 꺼낸다
    AFEBuildPiece* Current = Frontier[BestIndex];
    Frontier.RemoveAtSwap(BestIndex);
    const uint8 CurrentDistance = OutDistance[Current];

    // 가구 · 방어시설은 다른 피스를 받치지 않는다
    if (!CanSupportOthers(Current)) continue;

    for (AFEBuildPiece* Neighbor : Adjacency[Current])
    {
        uint8* NeighborDistance = OutDistance.Find(Neighbor);
        if (NeighborDistance == nullptr) continue;

        const int32 Candidate = FMath::Min<int32>(
            CurrentDistance + Neighbor->GetSupportCost(), Unreachable);
        if (Candidate < *NeighborDistance)
        {
            *NeighborDistance = static_cast<uint8>(Candidate);
            Frontier.AddUnique(Neighbor);
        }
    }
}
설계
  • 피스 연결을 그래프로 보고, anchor에서 출발하는 다익스트라로 모든 피스의 거리를 구합니다.
  • 그래프를 두 개 유지합니다. 청사진까지 포함한 설계 그래프로 배치를 판정하고, 완성된 피스만 담은 실제 그래프로 붕괴를 판정합니다.
  • 여러 피스가 한꺼번에 바뀌면 다음 틱에 한 번만 재계산하도록 묶었습니다.
문제 해결
  • 처음에는 "연결이 하나도 없으면 anchor"로 판정했더니, 공중에 매단 계단이 받침을 잃는 순간 오히려 anchor가 되어 떠 있었습니다.
  • 코드 리뷰 후 바닥면이 실제 지형과 닿아 있는지로 판정을 바꾸고, 배치 예측 · 완성 판정 · 재계산이 같은 함수 하나를 쓰게 했습니다.

청사진 · 재질 · 수리 Blueprint & Durability

청사진과 재료 투입
  • 배치하면 먼저 반투명 청사진이 생기고, E를 눌러 재료를 넣어야 완성됩니다.
  • 구조물은 처음 넣은 재료로 재질이 정해집니다. 나무를 넣으면 나무 벽, 돌을 넣으면 돌 벽이 됩니다.
  • 청사진을 철거하면 넣은 재료를 100% 돌려받습니다.
망치로 수리 · 업그레이드
  • 망치를 들고 좌클릭하면 수리, 우클릭하면 다음 재질로 업그레이드합니다.
  • 업그레이드는 액터를 새로 만들지 않고 정의 데이터만 교체해서 위치 · 소켓 · 문 열림 상태가 유지됩니다.
  • 수리 비용은 깎인 체력 비율 × 재료 × 0.5입니다.

가구 & 방어시설 Base & Defense

가구 5종

문 · 침구 · 작업대
  • 문: 열림 상태를 복제하고, 열고 닫을 때 NavMesh에 반영
  • 침구: 플레이어별 리스폰 위치 등록
보관함 · 화로
  • 보관함: 칸 수 = 용량, 한 칸 최대 999개, 넣기 · 꺼내기 순서로 아이템 증발 방지
  • 화로: 연료 · 재료 · 결과 3칸, 0.5초 서버 타이머로 가공, 할 일이 없으면 자동 소화

함정 AFEBuildTrap

  • 스파이크 · 철조망은 자체 AbilitySystemComponent와 AttackPower를 가지고, 전투 담당 팀원의 GAS 피해 경로를 그대로 써서 피해를 줍니다.
  • 밟고 있는 대상마다 1초 간격으로 피해를 주고, 줄 때마다 함정 자신의 내구도도 깎입니다. 철조망은 적에게 감속 태그를 붙입니다.
  • 피해는 서버만 계산하므로 함정의 ASC는 복제하지 않도록 해 네트워크 비용을 줄였습니다.

탑승형 발리스타 AFEBuildBallista

  • E로 탑승하면 서버가 발리스타의 Owner를 탑승자로 바꿉니다. 그래서 그 플레이어만 발사 · 조준 RPC를 보낼 수 있습니다.
  • 조준은 내 화면에서는 즉시 반영하고, 다른 플레이어에게는 int8 각도로 초당 10회 이하만 보냅니다. 패킷을 잃어도 0.5초마다 다시 보내 맞춰집니다.
  • 발사는 서버가 탄약 · 장전 시간 · 볼트 로드 여부를 확인한 뒤, 오브젝트 풀에서 투사체를 꺼내 쏩니다.
  • 장전 완료 시각을 복제해, 탑승자가 바뀌어도 모든 화면이 같은 장전 상태를 봅니다.
  • 탑승 중 사망 · 파괴 · 철거 시 자동으로 내리고 입력과 카메라를 원래대로 돌립니다.
// FEBuildBallista.h
/** [Server RPC] 발사. 조준은 정밀값(float) —

UFUNCTION(Server, Reliable, WithValidation)
void ServerFire(float Yaw, float Pitch);

void ServerSetAim(int8 Yaw, int8 Pitch);

/** [Client RPC] 서버만 아는 실패 사유를

상호작용 Interaction

문 열기, 청사진 재료 투입, 보관함 열기, 발리스타 탑승, 아이템 줍기가 모두 IFEInteractable 인터페이스 하나로 동작합니다. C++과 블루프린트 양쪽에서 구현할 수 있게 BlueprintNativeEvent로 만들었습니다.

// FEInteractable.h
class IFEInteractable
{
    /** 클라/서버 공용. 대상 필터와 프롬프트 표시 */
    UFUNCTION(BlueprintNativeEvent, BlueprintCallable)
    bool CanInteract(AActor* InstigatorActor) const;

    /** 프롬프트 문구. 예: "문 열기" */
    UFUNCTION(BlueprintNativeEvent, BlueprintCallable)
    FText GetInteractText(AActor* InstigatorActor) const;

    /** [Server Only] 거리와 CanInteract 재검증 후 호출 */
    UFUNCTION(BlueprintNativeEvent, BlueprintCallable)
    void Interact(AActor* InstigatorActor);

    /** [Client Only] 서버 성공 후 UI 열기 · 로컬 연출 */
    UFUNCTION(BlueprintNativeEvent, BlueprintCallable)
    void InteractLocal(AActor* InstigatorActor);
};
  1. 클라이언트 · 대상 찾기
    조준한 액터의 CanInteract, 프롬프트 문구를 MVVM으로 표시
  2. 서버 · 재검증
    UFEInteractionComponent가 거리와 CanInteract를 다시 확인
  3. 서버 · Interact
    문 열림, 재료 투입 같은 상태 변경
  4. 클라이언트 · InteractLocal
    패널 열기 등 요청한 플레이어 화면에서만 처리

빌드 모드 중에는 회전 키와 상호작용 키(E)가 겹치는 문제가 있어서, 빌드 모드에 로컬 게임플레이 태그 State.Building을 붙이고 상호작용 컴포넌트가 이 태그가 있을 때 동작하지 않도록 막았습니다.

멀티플레이 설계 Network Design

서버 권한 원칙
  • 배치 · 철거 · 투입 · 수리 · 발사 같은 게임 로직은 모두 서버에서만 실행하고, 클라이언트는 요청만 보냅니다.
  • 모든 Server RPC에 _Validate를 두고, 서버가 거리 · 도구 · 재료를 다시 확인합니다.
  • 복제 값은 작게 유지합니다. 체력은 uint8 퍼센트, 회전은 단계 값, 조준은 int8입니다.
요청 폭주 방지

수리 · 업그레이드 · 발사 · 조준 요청에 같은 간격 제한 함수를 씁니다. 네트워크 지터로 조금 일찍 온 요청은 받아 주되, 평균 간격은 지키도록 다음 허용 시각을 누적합니다.

// FEBuildingTypes.h
inline bool ConsumeRequestSlot(
    double& NextAllowedTime, double Now,
    double Interval)
{
    if (Now < NextAllowedTime - Interval * 0.5)
        return false;
    NextAllowedTime = FMath::Max(
        NextAllowedTime, Now) + Interval;
    return true;
}

기능을 바로 구현하기보다, 작업 내용과 완료 조건을 GitHub Issue에 먼저 정리해 팀원들과 공유합니다. 모든 코드 작업은 Issue에서 출발해 기능 단위 브랜치로 나누고, 구현 후에는 반드시 2인 PIE에서 멀티플레이 동작을 검증한 뒤 PR을 올립니다. 지금도 이 흐름으로 개발하고 있습니다.

  1. Issue 정의
  2. 기능 구현
  3. PIE 멀티플레이 테스트
  4. Pull Request & Review
팀원 시스템과의 경계
  • 인벤토리가 아직 없을 때부터 IFEBuildInventoryProvider 인터페이스와 임시 Mock 컴포넌트로 개발했습니다. 실제 인벤토리가 오면 어댑터 하나만 바꾸면 됩니다.
  • 공용 캐릭터 C++ 파일은 수정하지 않고, 입력은 GAS 어빌리티 바인딩으로 붙였습니다.
  • 구조물 피해는 전투 담당의 IFE_Damageable 인터페이스로 받아, 좀비 공격 · 함정 · 발리스타가 같은 경로를 씁니다.
코드 리뷰
  • 리뷰 의견은 코드와 대조해 반영할 것과 근거를 들어 유지할 것을 나눴습니다. 발리스타 PR에서는 10건을 반영했습니다.
  • 리뷰 후속으로 건설 컴포넌트에서 HUD를 분리하고, 발리스타가 탑승을 스스로 처리하도록 구조를 정리했습니다.
